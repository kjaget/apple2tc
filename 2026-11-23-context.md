# Session context: generation-aware Simple C

## Current iteration: metadata-driven dispatch, Review Gate 3

Iteration 2 replaced per-instruction checks with block-entry guards and
targeted continuations. Iteration 3 now selects using write-maintained
whole-state and per-block mismatch counters rather than reading simulated
memory from selector helpers. The detailed implementation, generated block
example and review status are in the
[block-oriented implementation plan](docs/plans/2026-11-25-code-generation-block-dispatch-implementation.md)
and the updated [living design](docs/plans/2026-11-17-code-generation-switching.md).

At each dispatch PC, the selector uses only candidate block-validity units
containing that PC, prefers the caller's active generation if valid, and
otherwise requires a unique candidate. The write hook sets the dirty flag
only when a changed value affects indexed static code. Unknown and ambiguous
code remain fail-closed; do not assume the next recorded generation is the
runtime successor.

The same-block fixture demonstrates a possible case but does not indicate its
frequency. The current working assumption is that modifying a later
instruction in the same original block is exceptional (an educated guess, not
a measured fact). Optimize the common path for a single block-entry decision
and intact sequences; add targeted continuation handling for possible
same-block hazards rather than checking every instruction or store. Keep
computed destinations conservative and revisit this assumption as broader
evidence becomes available.

Implement in small iterations, show generated C and validation evidence to a
human at each review gate, and update both the living design and new plan
after feedback before continuing.

Iteration 0 captured the generated-output baseline and reached Review Gate 0.
The user approved the first implementation slice and clarified that
same-block modification should be treated as an exceptional path based on an
unproven frequency guess, not as justification for per-instruction guards.
Iteration 1 added sparse whole-state and per-block mismatch counts; Review
Gate 1 was approved. Iteration 2 removed instruction-by-instruction guard
emission and added direct and indirect same-block boundary coverage. The user
approved Iteration 2, noting that source-size counts are evidence rather than
the optimization goal. Iteration 3 replaced RAM-scanning selection with
counter-based candidate selection and is ready for human review at Gate 3.

## Original goal (initial implementation completed)

Implement the first working step toward generation-aware generated C, based on
the design and task breakdown in
[`docs/plans/2026-11-17-code-generation-switching.md`](docs/plans/2026-11-17-code-generation-switching.md)
and
[`docs/plans/2026-11-20-code-generation-switching-implementation.md`](docs/plans/2026-11-20-code-generation-switching-implementation.md).
The motivating problem is that ordinary Simple C emits one fixed instruction
per PC, so it can execute stale code after self-modifying instructions replace
code that has already run.

## Relevant prior work

The preceding implementation tasks established and tested:

- Indexed generation tracking storage without changing collector semantics.
- Materialization and disassembly of independent cumulative code states using
  the input binary, `FirstInstructions`, and recorded generation segments.
- Transition evidence and fixtures for installed/replaced/restored code,
  delayed and indirect writes, unchanged code, same-block modifications, and
  code written through the stack.
- Existing run-data generations are partial byte-segment snapshots, not full
  snapshots or a complete event log. Absence from a segment does not prove a
  byte was unchanged.

## Task 6 changes in this session

Added an opt-in `--generation-aware` mode for Simple C:

- Materializes each run-data generation and emits a separate complete static
  PC switch for each distinct low-memory code state.
- Tracks CPU writes through the generated runtime's shared `ram_poke_impl`
  path, including stack writes. Only writes that change indexed static-code
  validity set the dirty flag; revalidation occurs at block entry or selected
  post-write continuations.
- Uses direct low-memory reads for matching, avoiding side-effecting I/O reads.
  Operand bytes known to vary are excluded from opcode-state matching and
  generated code uses dynamic reads for those operands.
- Keeps non-writing instructions contiguous and emits targeted continuation
  checks after stores that may reach static bytes in the current block's
  remaining suffix. Resume cases preserve the original block-entry
  probe/debug dispatch and adjust the remaining cycle charge when switching.
- Tests transition debug/probe sequences and normalized cycle totals against
  the interpreter for both inter-block and same-block changes. Generated C
  was exercised with repeated one-cycle calls and a single 1000-cycle call.
- Tests ordinary `--simple-c` execution without `--generation-aware` on an
  unchanged-code fixture and compares its result bytes to the interpreter.
- Reports unknown or ambiguous code rather than silently executing stale
  instructions.
- Leaves ordinary `--simple-c` output on its existing path.

The first iteration deliberately has a restricted scope: ordinary low memory
only. It rejects `--generation-state`, `--no-gen`, ROM, language-card,
`--code-at`, and `--inline-str` combinations. It requires run-data containing
`FirstInstructions` and at least one generation entry.

## Validation

Passed:

```sh
ninja -C build tools/apple2tc/apple2tc
bash tests/generation-switch-test.sh build
bash -n tests/generation-switch-test.sh
git diff --check
```

On the main switch fixture, generated C is 29,833 bytes / 874 lines with
12 dirty guards and metadata-selector sites, down from 282 dirty-guard sites
in Iteration 0; there are no interior resume cases. The same-block fixture
emits 8 guards and 2 resume cases. The unused generated unit-descriptor table
was removed. These are source-shape measurements, not runtime speedup claims.
Tests assert a single guard in the ordinary `$0300` block, targeted
direct/indirect same-block boundaries, no simulated-RAM reads in selector
helper bodies, and no emission of the unused table.

Care must be taken that builds continue to work using the normal path of
running `ninja` from the build directory.

The generation-aware replay matched interpreter RAM for the installed,
replaced, and restored fixture; delayed writes; preloaded code with a changed
instruction length; and a same-block opcode replacement. A modified immediate
operand was read dynamically, and an injected unknown opcode failed with an
explicit diagnostic. Transition probe/debug sequences and normalized cycles
matched the interpreter for inter-block and same-block changes across repeated
`run_emulated()` calls and a larger single budget. Ordinary Simple C also
replayed an unchanged-code fixture without the generation-aware option.

The complete `tests/run-tests.sh` suite was also attempted from `tests/`. It
stopped at `FAIL: a2mcp transcript reboot differs from its baseline`; the
generation-aware test itself passed separately. This failure has not been
investigated as part of this task.

## Remaining work and cautions

This implementation is not yet a general or fully validated runtime solution.
Review Gate 3 was approved. The plans still mark these follow-ups open:

- Narrow selector work to the active generation and exact remaining
  block/suffix range, with tests for partial states and ambiguity.
- Specialize post-write continuation selection using the effective address
  and old/new value already available at the write hook.
- Test broader transition patterns and event timing beyond the focused
  inter-block and same-block fixtures.
- Compare full CPU/register and memory state, not only selected result bytes.
- Expand ordinary no-option regressions and determine whether support can
  safely extend to higher memory, language-card mappings, or IR output.
- Document the option and its supported subset in user-facing usage docs.

The worktree also contained unrelated generated game-code changes and EOS
working files before/after this task; they were not part of the Task 6 changes
and were left untouched.
